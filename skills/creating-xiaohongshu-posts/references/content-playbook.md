# 小红书内容 Playbook

## 先确定一条读者承诺

用一句话写清：`这篇内容让哪类人，在什么场景下，获得什么具体收获。`

一篇只保留一个主要承诺。素材很多时，优先选择细节最充分、最有新信息的一条，其余内容留作后续选题。

## 标题

标题的任务是准确放大正文里最值得点开的部分，不额外制造正文无法兑现的悬念。控制在 20 个中文字或英文单词内。

常用角度：

- 结果：`我终于用 Codex 发出了第一篇小红书`
- 卡点：`小红书发布超时，根因竟是标题框`
- 适用对象：`给独立开发者的会议纪要工作流`
- 反常识 / 发现：`MCP 没坏，是页面遮住了输入框`
- 清单：`本地跑 AI 前，我会先检查这 5 件事`

主标题选择标准：具体、自然、正文能兑现。另给两个角度不同的备选，不做同义改写。

## 开头与正文

开头用 1–3 行交代场景、问题或结果。删除“今天想和大家分享”“相信很多人都”等可以用于任何主题的句子。

按帖子类型组织正文：

### 经历 / 开发记录

1. 原本想完成什么
2. 实际卡在哪里
3. 哪条线索改变了判断
4. 怎么解决
5. 解决后有什么变化或下一步

技术细节只保留能解释转折的部分。让非同领域读者也能理解“为什么难”和“为什么这个发现有意思”。

### 教程

1. 先展示完成后的结果
2. 说明适用对象和前提
3. 每步写成“动作 + 预期现象”
4. 补充最容易失败的一两个点
5. 用可执行的检查清单收尾

### 产品介绍

1. 用一个具体使用场景开场
2. 写清旧方法的摩擦
3. 展示产品如何改变这一步
4. 给一个输入 → 输出示例
5. 用问题、试用或反馈邀请收尾

避免替用户编造“我做了很久”“很多用户都说”“效率提升 80%”之类的背书。

### 测评 / 对比

先说明比较标准，再写实际观察。结论要指出分别适合谁，避免只有参数罗列。

### 清单 / 收藏

先给筛选标准，再按场景分组。每项都提供一个判断或使用建议，不做只有名称的堆砌。

## 语言与节奏

- 保留用户原话中有辨识度的表达，顺一下逻辑即可。
- 一段表达一个意思，通常 1–3 句。
- 用具体名词和动词：写“标题框被浮层挡住”，少写“遇到了一些兼容性问题”。
- emoji 只有在帮助分段或符合用户原本语气时才用；通常 0–3 个足够。
- 结尾给自然的下一步：一句结论、一个真实问题，或用户接下来准备做什么。

## 封面与配图

封面只传达一个信息，文案优先控制在 6–12 个字，能和标题互补而不是重复。

图文帖可按以下顺序设计：

1. 封面：结果或核心冲突
2. 场景：问题发生在哪里
3. 过程：关键步骤、截图或对比
4. 结果：修复后画面、产物或数据
5. 总结：方法、清单或结论

有真实截图时优先使用真实截图，并裁掉无关区域。需要生成视觉时，先写清尺寸、主体、画面层级、封面文字和风格，再调用图像生成工具。

## 标签

默认选 3–6 个，不带 `#`：

- 1–2 个主题词：如 `Codex`、`MCP`
- 1–2 个人群或场景词：如 `独立开发`、`程序员日常`
- 1 个内容类型或具体问题：如 `开发踩坑`、`小红书自动化`

删除与正文关系很弱的泛词，不为凑数量添加标签。

## 默认交付格式

```markdown
主标题：
备选标题：
- 
- 

封面文案：

正文：

配图方案：

标签：标签1、标签2、标签3
```
